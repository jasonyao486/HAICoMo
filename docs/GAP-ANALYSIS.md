# HAICoMo 0.6.0 与多 agent 完全控制台的差距

日期：2026-10-20（0.6.0 更新；0.5.0 与 0.3.3 结论见下文历史段落）。结论：已形成可验证的本地管理、提案审阅和人工验收闭环；凡提供 headless 命令行的客户端均可后台调用，支持 ACP 的客户端和 Claude 的权限请求可在 HAICoMo 中回答；接力支持最多三阶段 × 三个并行任务，阶段间传递结构化交付记录，git 项目的并行任务各用一个工作副本并在阶段完成时合并，并可在逐个接力同意后无人值守运行。它仍不能成为任意客户端、任意电脑、全天候运行的统一执行平台。不用单一百分比掩盖这些不同层次的差距。

## 0.6.0：prd_draft → 当前 → 理想

| 方面 | prd_draft 的要求 | 0.6.0 现状 | 理想状态与剩余差距 |
|---|---|---|---|
| 智能体的提问与权限 | 人类作为控制台，能在 app 中操作本地智能体 | Codex、ACP 客户端、Claude 宿主通道的权限请求都在 HAICoMo 弹窗中回答；无人值守时逐条代答并记录 | Cursor、DeepSeek Harness 仍依赖各自的权限参数；ACP 实现以 v1 schema 为准，各家实现成熟度不一 |
| 交接内容 | 交接物是给下一个 agent 的提示词 | 带任务的提示词要求交付记录；接力传递结构化记录 | 记录未经核实；产物“存在”只检查文件，不检查内容 |
| 验收 | 选择交付物后去 Finder 验收 | 验收区显示交付记录和产物路径；附意见退回并直接发给智能体 | 退回后仍需人工再次验收 |
| 并行冲突 | 多 agent 并行读写同一项目 | git 项目的同阶段任务各用工作副本，阶段完成时合并，冲突交给人 | 非 git 项目仍共享目录；合并冲突不自动解决 |
| 客户端覆盖 | 各家本地 agent | 16 个客户端，新增 Hermes；列表 A–Z | Hermes 未在真实安装上运行 |

## 三类壁垒

**第三方接口限制。** 每个客户端的登录、会话、模型目录、权限和工具事件不同。有稳定 CLI/API 的产品需要独立适配器和版本验证；只有 GUI 的客户端不能仅凭“打开应用”就声称已发送并监控。未知实际模型不得从客户端名字或旧会话猜测。接口可能变化，能力发现不等于长期兼容保证。

**当前产品边界。** 人工批准和验收是明确保留的控制点；一个人类、本地项目、无自动重试未知结果是当前决定。0.5.0 按用户决定放开了多步链路：终止条件是“任一任务未交付即停在本阶段”，责任由逐个接力的人工保存与（无人值守时）逐个接力的同意承担；自动验收仍不提供，预算上限仍未定义。活动允许人类删除，因此它不是不可篡改的合规审计系统。

**尚未实现的工程能力。** 常驻调度服务、远程执行代理、统一转录/工具流、成本预算、可靠断线重连和分布式数据层仍需设计与实现。当前 SQLite 文件、主机锁和同步盘不能替代服务器事务。应用中的未知状态是诚实的观测边界，不是可由动画补全的数据。

## 0.5.0：prd_draft → 当前 → 理想

| 方面 | prd_draft 的要求 | 0.5.0 现状 | 理想状态与剩余差距 |
|---|---|---|---|
| 多智能体后台调用 | 一个人类管理多个 AI agent，跨平台协作 | 15 个客户端可检测；12 个有后台适配器，按已装 CLI 的帮助文本启用并标注证据等级；Cursor → DeepSeek 的跨智能体接力已真实跑通（见 TESTING-0.5.0）；Kimi/Gemini/Qwen 等可与 Codex、Claude 混编进同一接力 | Kimi 与 7 个按文档适配的客户端仍待真实成功路径；Grok Bot 等无 CLI 的客户端只能半自动；Windows 上新适配器的安装路径未实机验证 |

## 0.4.0：prd_draft → 当前 → 理想

| 方面 | prd_draft 的要求 | 0.4.0 现状 | 理想状态与剩余差距 |
|---|---|---|---|
| 版本维护 | 单一控制台，减少在多个工具间切换 | 设置内检查官方发布、显示更新内容、下载进度（速度/剩余时间/可取消）、SHA-512 校验、用户确认后重启安装并恢复标签；默认自动检查只提示，可关闭 | Windows 发布者签名；更新失败时的自动回退；离线或无法访问 GitHub 时的镜像源（需另行决定） |
| 找回决定与参数 | 人类始终掌握项目全貌 | 总览关键词检索任务（含归档）、修订（含拟修改文本与审阅备注）、会议与备注，分组高亮并直达原条目 | 语义检索、跨项目检索、按日期/人员筛选、活动记录与接力内容检索；这些需要单独的产品决定，本版按要求不引入 AI |
| 客户端识别 | 多智能体团队可辨认 | WorkBuddy 使用官方应用图标，CodeBuddy 使用彩色标志，双端共用 | WorkBuddy 在 Windows 的真实安装路径尚未在真机验证，检测可能需要手动指定路径 |

真实验证边界：Mac 的应用内替换、取消下载、未保存草稿保存、重启恢复以及篡改签名被拒绝，均用本机 Apple Development 签名的 0.4.0→0.4.1 测试应用完成；正式 Developer ID 发布版之间的首次真实替换须等 0.4.0 公开后、从已安装 0.3.5 引导升级时确认。Windows 的真实应用内替换由 CI 非管理员账户中的 0.4.0→0.4.1 夹具场景验证，并作为发布闸门；不以 Mac 结果代替。

## 0.3.2 界面修订

首页独立于项目标签，保留页面和草稿，收起侧栏图标统一；活动列表与总览使用明确身份的短角色，展开详情保留原始信息。这些更新提高日常管理体验，不扩大多智能体执行能力或云端协作范围。0.3.2 发布验证见 [测试记录](TESTING-0.3.2.md)。0.3.1 发布与历史报告保留，本轮新增的能力集中在界面和导航。

## 0.3.1 解决的差距

- 活动记录可单条确认删除；v5 独立历史返工统计避免删除改变业务指标，迁移前备份。
- 10 个父任务各 5 个子任务有可访问、无节点重叠的关系与树布局；支持缩放、适应、拖动和明确模型的公司标志。密集图仍需放大阅读，依赖连线不承诺完全无交叉。
- 相对交付物路径跨系统统一；外部绝对路径标明重新定位责任。
- 增强接力拥有独立工位和正面双人沙发，默认/增强、浅深色及减少动态共用业务状态。
- GitHub 下载与反馈入口、MIT 源码与第三方素材许可分界、素材白名单构建和四语完整手册形成可维护的公开交付。

## 云盘、NAS 与 GitHub 评估

| 放置方式 | 是否按预期工作 | 使用条件 |
|---|---|---|
| 本地目录 | 当前主要场景 | 一次一个应用写入者；文件协议可并行投递 |
| 已完整下载的云盘目录 | 可作为离线搬运，存在同步工具边界 | 停止运行、暂停接力、退出应用后同步整个目录；另一机等下载完成再打开 |
| NAS/SMB/NFS 上的活动 SQLite | 不承诺可靠，建议不用 | 网络文件系统的锁、缓存和故障语义可能损坏数据库；本地工作副本更合适 |
| Git 仓库中的项目管理目录 | 可用于关闭后的版本搬运，不是合并协作 | 包含入口、隐藏数据和所需交付物；打开期间不 pull/切分支，不合并 SQLite 冲突副本；避免公开隐私 |
| GitHub URL / 仅入口文件 | 不能直接工作 | URL 不是本地项目；入口不是数据库，需要完整下载本地目录 |
| 两台电脑同时打开同一同步项目 | 不支持 | 主机锁接管不是分布式协调，不能保证云盘传播时序 |

SQLite 官方说明网络文件系统可能破坏锁和持久性假设：[SQLite over a network](https://www.sqlite.org/useovernet.html)。备份 ZIP 只含管理数据，不含实际交付物；搬运源代码和交付物是单独责任。

## 建议的后续次序

1. 扩展 Windows 消费设备、受管理电脑及实际 CLI 版本覆盖，保留已完成的非管理员令牌验收证据。
2. 评估 Windows 发布者签名，使应用内更新同时校验发布者；保留 0.4.0 已验证的真实替换与签名拒绝恢复证据。
3. 深化现有两类 runner 的对话/工具可观测性与断线恢复，优先让未知和权限等待可诊断。
4. 按稳定接口增加其他客户端，保留每个适配器的可复现版本矩阵。
5. 若确实需要多机全天候控制，另立服务器数据层与远程执行设计；不要用同步盘补丁代替。

当前验证状态见 [0.4.0 验证记录](TESTING-0.4.0.md)；旧版本界面与兼容性记录仅用于追溯。
