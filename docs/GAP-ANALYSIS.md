# HAICoMo 0.3.2 与多 agent 完全控制台的差距

日期：2026-10-07。结论：已形成可验证的本地管理、提案审阅和人工验收闭环；对受支持的 Codex/Claude 安装具备后台交接与一步接力。它仍不能成为任意客户端、任意电脑、全天候运行的统一执行平台。不用单一百分比掩盖这些不同层次的差距。

## 完成程度与证据

| 维度 | 当前完成程度 | 证据 | 还缺什么 |
|---|---|---|---|
| 管理 | 基本闭环完整 | 任务/子任务、前置、日期、备注、修订提案、人工验收、归档；`core.test.ts`、`v2.test.ts`、桌面测试 | 资源预算、成本、复杂里程碑及多用户权限模型未实现 |
| 执行 | 两类客户端可托管，其他半自动 | `providers/`、`providers.test.ts`；Codex App Server、Claude CLI；模型/强度/模式能力目录、启动、取消 | 其他客户端逐一适配；不能注入任意现有 GUI 会话；当前测试使用 fixture，不等于所有线上 CLI 版本已验收 |
| 监控 | 有状态、权限应答、失联/未知、可观测时长 | runner 生命周期、后台任务、`office-updates.test.ts`、`tabs.spec.ts` | 全量对话流、跨客户端统一工具轨迹、可靠成本核算、外部运行的可信身份未实现 |

| 跨机协作 | 关闭应用后的完整目录搬运可行 | 身份/epoch、锁接管、路径规范、备份恢复测试 | 同时在线编辑、冲突合并、分布式锁/事务、远程 runner 均未实现 |

## 三类壁垒

**第三方接口限制。** 每个客户端的登录、会话、模型目录、权限和工具事件不同。有稳定 CLI/API 的产品需要独立适配器和版本验证；只有 GUI 的客户端不能仅凭“打开应用”就声称已发送并监控。未知实际模型不得从客户端名字或旧会话猜测。接口可能变化，能力发现不等于长期兼容保证。

**当前产品边界。** 人工批准和验收是明确保留的控制点；一个人类、本地项目、一步接力、无自动重试未知结果是当前决定。放开多步链路或自动验收需要重新定义权限、预算、终止条件与责任，不能只添加一个循环。活动允许人类删除，因此它不是不可篡改的合规审计系统。

**尚未实现的工程能力。** 常驻调度服务、远程执行代理、统一转录/工具流、成本预算、可靠断线重连和分布式数据层仍需设计与实现。当前 SQLite 文件、主机锁和同步盘不能替代服务器事务。应用中的未知状态是诚实的观测边界，不是可由动画补全的数据。

## 0.3.2 界面修订

首页独立于项目标签，保留页面和草稿，收起侧栏图标统一；活动列表与总览使用明确身份的短角色，展开详情保留原始信息。这些更新提高日常管理体验，不扩大多智能体执行能力或云端协作范围。0.3.2 发布验证见 [测试记录](TESTING-0.3.2.md)。0.3.1 发布与历史报告保留，本轮新增的能力集中在界面和导航。

## 0.3.1 解决的差距

- 活动记录可单条确认删除；v5 独立历史返工统计避免删除改变业务指标，迁移前备份。
- 10 个父任务各 5 个子任务有可访问、无节点重叠的关系与树布局；支持缩放、适应、拖动和明确模型的公司标志。密集图仍需放大阅读，依赖连线不承诺完全无交叉。
- 相对交付物路径跨系统统一；外部绝对路径标明重新定位责任。
- 增强接力拥有独立工位和正面双人沙发，默认/增强、浅深色及减少动态共用业务状态。
- GitHub 下载与反馈入口、MIT 源码与第三方素材许可分界、素材白名单构建和四语完整手册形成可维护的公开交付。

## 云盘、NAS 与 GitHub 评估

| 放置方式 | 是否按预期工作 | 使用条件 |
|---|---|---|
| 本地目录 | 当前主要场景 | 一次一个应用写入者；文件协议可并行投递 |
| 已完整下载的云盘目录 | 可作为离线搬运，存在同步工具边界 | 停止运行、暂停接力、退出应用后同步整个目录；另一机等下载完成再打开 |
| NAS/SMB/NFS 上的活动 SQLite | 不承诺可靠，建议不用 | 网络文件系统的锁、缓存和故障语义可能损坏数据库；本地工作副本更合适 |
| Git 仓库中的项目管理目录 | 可用于关闭后的版本搬运，不是合并协作 | 包含入口、隐藏数据和所需交付物；打开期间不 pull/切分支，不合并 SQLite 冲突副本；避免公开隐私 |
| GitHub URL / 仅入口文件 | 不能直接工作 | URL 不是本地项目；入口不是数据库，需要完整下载本地目录 |
| 两台电脑同时打开同一同步项目 | 不支持 | 主机锁接管不是分布式协调，不能保证云盘传播时序 |

SQLite 官方说明网络文件系统可能破坏锁和持久性假设：[SQLite over a network](https://www.sqlite.org/useovernet.html)。备份 ZIP 只含管理数据，不含实际交付物；搬运源代码和交付物是单独责任。

## 建议的后续次序

1. 完成 Windows 真机安装、文件关联、托盘、实际 CLI、人工升级和卸载保留数据验收。
2. 完成签名、公证、真实旧版升级/失败恢复，再决定自动安装渠道。
3. 深化现有两类 runner 的对话/工具可观测性与断线恢复，优先让未知和权限等待可诊断。
4. 按稳定接口增加其他客户端，保留每个适配器的可复现版本矩阵。
5. 若确实需要多机全天候控制，另立服务器数据层与远程执行设计；不要用同步盘补丁代替。
