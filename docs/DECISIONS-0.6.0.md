# 0.6.0 决策记录：代你做出的选择

日期：2026-10-20。本文列出本轮开发中替你做出的每个决定，每条都写了“选择”和“理由”。所有决定都可以推翻，推翻时需要改动的位置写在“若要改”一栏。

下面几项是你亲自确认过的，本文不再重复论证：
- 版本号 0.6.0；
- 新增 Hermes，检测页按英文名 A–Z 排列；
- 左侧栏“接力任务”与“时间线”之间留出与“思维导图 / 协作办公室”相同的间隔；
- 通用 ACP 通道，同时给 Claude 加宿主权限通道，并同意在临时目录用你的 Claude 账号做真实测试；
- 结构化交付，但不增加操作；
- 退回并附意见：默认退回给原负责智能体，也可以另选一个智能体；
- git 项目中，同一阶段的并行任务各开一个 worktree，阶段完成时自动合并。

## 二、ACP 通道

| # | 问题 | 选择 | 理由 | 若要改 |
|---|---|---|---|---|
| 7 | 哪些客户端走 ACP | 已安装版本的帮助文本列出 ACP 入口（`acp` 子命令、`--acp` 或 `--experimental-acp`）时自动优先：Kimi、Hermes、Gemini CLI、Qwen Code、OpenCode、GitHub Copilot CLI、CodeBuddy、Qoder | 用户不用做选择；以已安装版本为准，旧版本自动保持命令行 | `adapters.ts` 的 `acp` 字段 |
| 8 | 不走 ACP 的客户端 | Codex 继续用 app-server，Cursor 和 DeepSeek Harness 继续用命令行；Claude 改用自己的宿主通道（见第三节） | Codex 的 app-server 已能回答权限且已验证；Cursor 和 DeepSeek 的 CLI 没有 ACP 入口；Claude 需要另装适配包才能走 ACP | 同上 |
| 9 | ACP 不能满足所选模型、模式、强度或会话时 | 在发出任务之前关掉 ACP 会话，改走命令行；没有命令行路径就报错 `ACP_OPTION_UNSUPPORTED` | 不在运行中途换通道；任务只发一次 | `LocalRunners.startAcp` |
| 10 | ACP 握手失败 | 有命令行路径就改用命令行；需要登录时报 `ACP_AUTH_REQUIRED`，不改走别的路径 | 握手失败时任务还没发出，改走命令行是安全的；需要登录时换路径也没用 | 同上 |
| 11 | HAICoMo 声明的 ACP 能力 | 不提供文件读写和终端（`fs`、`terminal` 都为 false），由智能体用自己的工具 | HAICoMo 不代替智能体读写文件，权限边界更清楚 | 同上 |
| 12 | 权限回答 | 人工点“允许”时选 `allow_once`（没有时选其他允许项），“拒绝”时选 `reject_once` | “总是允许”会被智能体记住，超出这一次运行 | `respond()` |
| 13 | 无人值守时的 ACP 权限 | 由 HAICoMo 逐条回答：非破坏性的选 `allow_once`；破坏性命令或删除项目外的文件选 `reject_once`；**从不自动选“总是允许”**；没有一次性选项时留给人 | 比 yolo 参数更安全，与 Codex 一致；每条决定都写进决策记录 | `autoDecide()` |
| 14 | 回合结束却没有回复也没调用任何工具 | 判为失败（`ACP_EMPTY_TURN`），提示检查登录或额度；接力显示“需要你处理” | 实测发现：Kimi 2.2.0 在额度用完时，ACP 模式下直接结束回合，不报错。判为完成就会误报交付 | `acpEnded()` |
| 15 | 加载旧会话时回放的历史 | 不计入本次输出 | 否则旧回复会被当成新结果 | `run.acp.loading` |

## 六、git 工作副本（worktree）

| # | 问题 | 选择 | 理由 | 若要改 |
|---|---|---|---|---|
| 34 | 何时使用 | 项目目录在 git 仓库内，并且某个阶段有 2 个及以上任务。新建接力时默认开启，可关闭 | 只有一个任务的阶段没有冲突，无需副本 | `stageUsesWorktrees`、接力编辑器 |
| 35 | 副本位置 | `<项目>/.haicomo/worktrees/<接力编号前 8 位>/<步骤号>`，分支 `haicomo/<接力编号前 8 位>/<步骤号>`；`.haicomo/.gitignore` 自动加上 `worktrees/` | 放在项目里，随项目一起；路径短，Windows 也适用 | `src/core/worktree.ts` |
| 36 | 重试 | 沿用同一个副本和分支 | 保留已经完成的部分工作 | `prepareWorktree` |
| 37 | 开工前检查 | 有提交记录、在某个分支上、没有进行中的合并或变基、已跟踪文件没有未提交改动（HAICoMo 自己的 `.haicomo` 和入口文件除外）；不满足就停在启动失败，写明原因 | 不替你处理未提交的改动 | `assertReady` |
| 38 | 智能体在哪里工作 | 副本中对应项目目录的位置；主项目的 `.haicomo` 加为额外可写目录（Claude、Cursor、Kimi 用 `--add-dir`，ACP 用 additionalDirectories） | 改代码在副本里，提案仍提交到主项目；Codex 要写主项目时会走它自己的审批 | `main.ts` 接力启动 |
| 39 | 合并时机 | 阶段全部交付后、下一阶段开始前，按步骤顺序逐个合并 | 你选的“阶段完成时自动合并” | `relayNext` 的 `merge` 动作 |
| 40 | 怎么合并 | 在副本中 `git add -A`（不含 `.haicomo`）并用你的 git 身份提交；再在主工作区 `git merge --no-ff`；成功后删除副本和已合并的分支（删不掉就保留） | 每个任务一个合并提交，以后可以单独回退 | `mergeWorktree` |
| 41 | 冲突 | 先 `git merge --abort`，再暂停接力，保留分支和副本，显示“我已手动合并，继续”；继续时再试一次，已经手动合并的分支会被直接通过 | 绝不自动解决冲突，也不强制操作 | 同上、`relay.resume` |
| 42 | 没有 git 身份 | 暂停接力，提示用 git config 设置 | 不冒用他人身份提交 | 同上 |
| 43 | 提交时是否跳过钩子 | 用 `--no-verify` | 用户仓库的提交前钩子可能要交互或运行很久，接力会卡住；合并后你仍可审阅 | 如需执行钩子，去掉 `--no-verify` |
| 44 | 接力被取消 | 保留副本和分支，并在接力上列出 | 可能有未合并的成果，由你决定如何处理 | `Relay.tsx` |
| 45 | 存储 | 接力上加可选的 `worktrees`，步骤上加可选的 `worktree`（路径、分支、合并时间、提交）；存储层只接受 `.haicomo/worktrees` 里的路径 | 不升级数据结构（仍为 v6）；0.5.0 打开时会忽略这些字段 | `store.ts` |
